# Spike S1 results: terminal dialog versus a waiting PermissionRequest hook

Run on 2026-10-19. Numbers only; no transcript content. Raw per-trial data: `S1-results.jsonl` (35 matrix trials). Plan: `S1-PLAN.md`.

Environment: Claude Code 2.1.302, macOS, model Haiku 5.5, Node v26.10.0. Interactive TUI in a pseudo-terminal driven by a Python stdlib `pty` harness (tmux was not installed and nothing was installed). Scratch folder, `--setting-sources project,local --settings <stub>`, `--permission-mode default`, an `ask` rule on `Bash(touch *)`. The stub hook logs and sleeps; it returned no decision in any trial.

## Verdict: PASS (with the caveats below)

| SPEC S1 criterion | Result |
|---|---|
| The terminal dialog is visible and answerable while the hook is still waiting | PASS. In 25 of 25 trials where the answer came while the hook slept (P1, P3, P4) the dialog took it: `Bash tool permission denied` was logged 54 to 94 ms after the key press, with the hook still alive |
| A terminal answer proceeds within 1 s | PASS. Maximum 94 ms across all trials |
| The hook process is killed or its channel closes within 2 s, 10 of 10 trials | PASS, 25 of 25. Claude Code sends SIGTERM to the hook: exec form 87 to 131 ms after the answer (process gone 109 to 252 ms); plain-wrapper form 114 to 628 ms (gone 118 to 825 ms) |
| Timeout case, 10 of 10 | PASS. With `timeout: 10` the hook got SIGTERM 9.53 to 9.93 s after it started; its heartbeat stopped at that moment; the dialog then accepted an answer 54 to 64 ms after the key press |
| A hook that returns late | Not reachable: the answer cancels the hook, so the late exit never happens (P3, 5 of 5: no END event, no stray process) |

## What this settles

- **A6 (order):** the dialog is shown and answerable in parallel with a pending hook. The terminal answer wins and Claude Code then cancels the hook.
- **A5 (timeout):** `timeout` is honored; on expiry the hook is cancelled with SIGTERM, within about 0.5 s of the configured value in these trials.
- **OQ8:** the planned waits (25 s server, 28 s hook, 30 s timeout) stand. A pending hook does not block the terminal prompt, so approve is viable and slice 2 does not need a new owner decision for this reason.
- **Cancel signal (R74, TM:X6, TM:D10):** a terminal answer reaches the hook as SIGTERM, so the hook's socket closes within about 0.25 s in the exec form. The server should treat a closed socket as "answered elsewhere" (the `outcome` of OQ2). The heartbeat and parent-pid rules stay as defence in depth.
- **Process form:** keep the `exec` form from SPEC section 9. It makes the hook a direct child of Claude Code and kills fastest (at most 0.25 s). The plain `sh -c` form also worked in 10 of 10 (no orphan), only slower and with a different parent.

## Other facts observed

- The hook payload keys are `session_id, transcript_path, cwd, scratchpad_dir, prompt_id, permission_mode, effort, hook_event_name, tool_name, tool_input`, 740 to 761 bytes for the probe. There is no `tool_use_id`, no `agent_id`, no pid. `prompt_id`, `scratchpad_dir` and `effort` are new to the spec.
- The matchers `*` and `Bash` both fire for the Bash tool (partial answer to S5).
- An empty hook output is logged as plain text and treated as no decision; the dialog then waits for the user.
- Hooks stay held until the folder is trusted. The trust prompt's highlighted default is "No, exit". Accepting trust adds one entry for the scratch path to `~/.claude.json`.
- Isolation held: across all matrix trials the debug log showed no hook execution other than the stub (0 foreign hook lines), and `~/.claude/settings.json` was byte-identical before and after. The account's MCP connectors (claude.ai Figma, Semrush, Notion) still connect during a session; `--setting-sources` does not exclude them.
- Cost and time: a P0 session took about 10 s and cost $0.0009 to $0.0042 (engine figure for turn 1; the 35 matrix trials each took 16 to 26 s).

## Incident during P0

In P0 session 3 a harness bug let a final `/exit` plus Enter land on a permission dialog it had not recognised, so one harmless empty file (`probe.txt`) was created in the scratch folder. No hook decision was involved. The harness was changed: the hook's own log is the dialog signal, Esc is the only key sent at a permission dialog, sessions end with Ctrl+C then SIGTERM, and the run aborts if `probe.txt` appears. It did not recur in the 37 sessions that followed.

## Caveats and what is NOT shown

- Only the deny path (Esc) was exercised, by design (the plan never allows). That an allow answered in the terminal also cancels the hook the same way is expected but UNVERIFIED.
- One Claude Code version (2.1.302), one OS, one model, the Bash tool only, interactive mode only (`-p` untested).
- A Python pty is not Terminal.app or iTerm2. The behaviour should not depend on the emulator, but that is UNVERIFIED (S4 and S17 still need real terminals).
- The hook never returned allow or deny, so the race where the hook decides first and the interaction with a second hook are untested (S3).
- The hook was stopped with SIGTERM and exited promptly. Whether Claude Code escalates to SIGKILL for a hook that ignores SIGTERM is untested (S2).
- The mechanism for the plain-wrapper kill (process group or relay) is unknown; only the outcome was measured.
