# Spike S5 (rest): matcher forms, trailing marker comment, cwd and env

Run 2026-10-19/20. Counts, tag names and key names only. Question (SPEC section 15, S5): which `PermissionRequest` entry form fires for every tool, and does the shell command with a trailing `# deskmates:v1` comment work? S1 had already covered the `exec` form, the settings `timeout` and a `Bash` matcher.

Method: a scratch folder (no repo files), `claude 2.1.302` driven through a Python pty harness (tmux is not installed), `--setting-sources project,local --settings <stub> --permission-mode default --model haiku`. One settings file held eight `PermissionRequest` entries at once, each running the same stub (logs the entry tag, tool name, payload key names, cwd, whether `node` is on `PATH`, and the names of `CLAUDE_*` env vars; prints nothing; exits 0), so one session shows which entry forms matched. Entries: `m-omit` (no `matcher` key), `m-star` (`"*"`), `m-empty` (`""`), `m-bash` (`"Bash"`), `m-write` (`"Write"`), `m-editwrite` (`"Edit|Write"`), `m-webfetch` (`"WebFetch"`), and `c-nocomment` (`"*"` with no trailing comment; every other command ends with `# deskmates:v1`). Command form: `[ -r "STUB" ] && exec node "STUB" TAG || exit 0 # deskmates:v1`. `ask` rules forced a dialog for `Bash(touch *)`, `Write`, `Edit` and `WebFetch`. Each session answered the dialog with Esc (deny) after 3.5 s, then ended with Ctrl+C twice and SIGTERM; nothing ran.

Safeguards held: the scratch work folder was unchanged after every trial (only the seed file, content unchanged); `~/.claude/settings.json` hash unchanged; `~/.claude.json` changed (it is rewritten by every live session) and now holds one new entry, `hasTrustDialogAccepted: true`, for the scratch path (approved by the owner). 15 Haiku sessions in total: 3 setup sessions (the trust prompt defaults to "No, exit", so the first Enter exited; later runs send Down then Enter), then 12 counted trials.

## Results (12 trials, 3 per tool)

| Tool | Entries that fired (every one of 3 trials) | Entries that did not |
|---|---|---|
| Bash | `m-omit`, `m-star`, `m-empty`, `m-bash`, `c-nocomment` | `m-write`, `m-editwrite`, `m-webfetch` |
| Write | `m-omit`, `m-star`, `m-empty`, `m-write`, `m-editwrite`, `c-nocomment` | `m-bash`, `m-webfetch` |
| Edit | `m-omit`, `m-star`, `m-empty`, `m-editwrite`, `c-nocomment` | `m-bash`, `m-write`, `m-webfetch` |
| WebFetch | `m-omit`, `m-star`, `m-empty`, `m-webfetch`, `c-nocomment` | `m-bash`, `m-write`, `m-editwrite` |

- Omitted `matcher`, `"*"` and `""` each fired for every tool in 12 of 12 trials. Named matchers fired only for their tool; `"Edit|Write"` is treated as an alternation.
- The trailing `# deskmates:v1` comment is safe: every entry with it fired exactly like `c-nocomment`, which has none.
- The hook process's working directory is the session directory in 12 of 12; `node` was on the hook's `PATH` in 12 of 12 (the harness environment came from the desktop app, so this does not prove a login-shell `PATH`; the self-healing guard already handles a missing `node`).
- Payload keys, identical in all trials: `cwd, effort, hook_event_name, permission_mode, prompt_id, scratchpad_dir, session_id, tool_input, tool_name, transcript_path` (no `tool_use_id`, `agent_id` or pid, as before).
- Env: the hook inherits the parent's environment, plus Claude Code's own `CLAUDE_*` variables (for example `CLAUDE_PROJECT_DIR`, `CLAUDE_PID`, `CLAUDE_TMPDIR`; most of the long list seen came from the desktop app that launched the harness, so only the existence of a populated `CLAUDE_*` set is claimed). Consequence: the hook must not trust or log its environment; it reads none.
- Not tested here: the settings `timeout` (S1 did), MCP tool names (S8), matcher regex edge cases beyond `A|B`.

## Verdict and consequence

**PASS.** The entry form for slice 1 is `{"matcher": "*", "hooks": [{"type": "command", "command": "<guard> # deskmates:v1", "timeout": 30}]}` (omitting `matcher` also works; `"*"` is explicit and was chosen). The `sh` guard with the trailing marker comment works unchanged. Plan Task 7 (`buildCommand`, the settings entry) and Task 2 (T-selfheal) use exactly this; the uninstall engine identifies the entry by the marker plus the exact recorded command.
