# Spike S2 results: what happens when the hook fails or misbehaves

Run on 2026-10-19. Numbers only; no transcript content. Raw per-trial data: `S2-S3-results.jsonl` (rows with `phase: "S2"`). Plan: `S2-S3-PLAN.md`.

Environment as in `S1.md`: Claude Code 2.1.302, macOS, Haiku 5.5, a Python `pty` harness, a scratch folder, `--setting-sources project,local --settings <stub>`, an `ask` rule on `Bash(touch *)`.

## Verdict

- **Rows 1 to 8: PASS.** In 30 of 30 sessions the normal dialog stayed live and answerable, and nothing was allowed or denied implicitly (`probe.txt` never appeared, no denial without a key press).
- **Rows 9a and 9b: FINDING, not a pass.** A valid allow printed before a non-zero exit, or before the hook killed itself, still took effect: the command ran in 6 of 6 sessions. Claude Code applies the first output line as it arrives and does not wait for the exit. Details and consequences below.

## Rows 1 to 8 (3 trials each; row 1 has 3)

| # | Hook behaviour | What Claude Code logged | Result |
|---|---|---|---|
| 1 | exit 1, no output | `Hook ... error: status code 1` | dialog live, answered 55 to 58 ms after Esc |
| 2 | exit 2, message on stderr | `error: status code 2` with the stderr text; not honored as a decision | dialog live, 59 to 62 ms |
| 3 | exit 0, truncated JSON | "starts with { but is not a JSON object, treating as plain text: JSON Parse error: Unexpected EOF" | dialog live, 55 to 57 ms |
| 4a | exit 0, plain text `allow` | "does not start with {, treating as plain text" | ignored; dialog live, 58 to 60 ms. A naive hook that prints the word "allow" allows nothing |
| 4b | exit 0, plain text `yes` | same | ignored; dialog live, 56 to 65 ms |
| 5a | exit 0, valid JSON with an unknown behaviour value | logged as an error (stdout echoed) | dialog live, 56 to 66 ms |
| 5b | exit 0, valid JSON with the wrong event name (a deny) | "Hook returned incorrect event name: expected 'PermissionRequest'" | error, nothing applied; dialog live, 57 to 61 ms |
| 6 | hook SIGKILLs itself, no output | `error: status code 1` | dialog live, 54 to 61 ms |
| 7 | ignores SIGTERM; terminal answer 4 s after the hook fired | SIGTERM reached the hook 4.12 to 4.17 s after START and was ignored | session proceeded at once (denial 61 to 73 ms); **the hook was force-killed about 1.35 to 1.40 s after SIGTERM** (last heartbeat at 5.52 s), 3 of 3 |
| 8 | hangs and ignores SIGTERM, `timeout: 10` | SIGTERM at 9.88 to 9.90 s, ignored | force-killed about 1.39 to 1.41 s later (last heartbeat 11.29 to 11.30 s), 3 of 3; the dialog was answerable afterwards (58 to 63 ms) |

"Force-killed" is inferred from the last heartbeat (the stub beats every 250 ms, so about plus or minus 0.25 s). In row 8 the liveness poll only started at the key press, so the heartbeat is the reliable time.

## Rows 9a and 9b (the security-relevant pair, 3 trials each)

| # | Hook behaviour | Result |
|---|---|---|
| 9a | prints a valid allow, then exits 1 | `executed` in 3 of 3: the allow took effect despite the failing exit |
| 9b | prints a valid allow, then SIGKILLs itself | `executed` in 3 of 3 |

The debug log shows why: Claude Code reads the first output line as soon as it arrives ("Checking first line for async", "Parsed initial response") and applies it. A later failure does not revoke a decision already given.

## What this settles and changes

- **Fail-open holds for every failure mode tried** (rows 1 to 8). R2 stands: every failure path exits 0 with empty output and the normal dialog appears.
- **R2 needs one more clause, and now has it:** any decision is printed as the LAST act, in a single write, with nothing after it. A crash after printing cannot be undone. The test `T-hook-failopen` should also assert that the script writes nothing before the verdict and does nothing after it that can fail.
- **R74 (parent poll and self-exit) stays defence in depth:** Claude Code does force-kill a hook that ignores SIGTERM, about 1.4 s after the signal, so a hung hook does not live on.
- A plain-text or malformed output never counts as a decision, so a bug that prints a word or a half-written object fails safe.
- This does not stop v0.2 at slice 1: the spec's stop condition (an implicit allow or deny in rows 1 to 8) did not occur. Slice 1's hook can only ever emit "no opinion" (R69).

## Caveats and what is NOT shown

- Three trials per row; one Claude Code version (2.1.302); macOS; the Bash tool; interactive mode in a Python pty.
- Rows 9a/9b used a valid allow, which let `touch probe.txt` run in the scratch folder (approved). It created one empty file per trial, set aside afterwards.
- Classification relies on the debug log (a denial logged before or after the key press) plus the presence of `probe.txt`, not on reading the screen.
- Hook types other than `command`, other tools, the `-p` mode and other terminals are untested.
- My earlier counter of "foreign hook lines" over-counts Claude Code's own JSON-parsing log lines in rows 5a and 5b; those were checked by hand and are not foreign hooks.
