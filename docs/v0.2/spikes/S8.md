# Spike S8: modes, subagents, headless, MCP

Run 2026-10-20. Counts and key names only. Question (SPEC section 15, S8): does the `PermissionRequest` hook fire under `acceptEdits`, `auto`, `plan`, `bypassPermissions`, in subagents, in `-p` headless runs and for MCP tools; does the payload carry `agent_id` or `agent_type`; are prompts serialized per agent?

Method: the S5 scratch setup (`claude 2.1.302`, Python pty harness, `--setting-sources project,local --settings <stub> --model haiku`, stub hook `matcher: "*"` that logs and prints nothing, every dialog answered with Esc). One `ask` rule for `Bash(touch *)` and one for the MCP tool, so a dialog is forced in every interactive mode. The MCP server is a 12-line local stdio stub in the scratch folder (one `echo` tool, no I/O), passed with `--mcp-config --strict-mcp-config`. 22 sessions: 3 per condition (the headless and MCP conditions include the pilot run).

## Results (3 of 3 in every condition)

| Condition | Dialog shown | Hook fired | `permission_mode` in payload | `agent_id` / `agent_type` in payload |
|---|---|---|---|---|
| default, MCP tool `mcp__s8stub__echo` | yes | yes (1 request) | `default` | no / no; extra key `mcp_server` |
| `acceptEdits`, Bash | yes | yes | `acceptEdits` | no / no |
| `auto`, Bash | yes | yes | `auto` | no / no |
| `plan` | no (the model called `ExitPlanMode`, not Bash) | yes, for tool `ExitPlanMode` | `plan` | no / no |
| `bypassPermissions`, Bash (ask rule present) | yes | yes | `bypassPermissions` | no / no |
| subagents (two launched in parallel), Bash | yes | yes, 2 requests | `default` | **yes / yes** (all 6 requests) |
| `-p` headless, Bash | no dialog possible | yes | `default` | no / no |

- The hook fires whenever Claude Code reaches a permission request, in every mode tested, and the payload reports the mode. Each condition was uniform across its 3 trials.
- Limit: the harness forced a prompt with an `ask` rule, so it shows the hook runs when a request is raised, not which calls each mode raises. A call a mode allows silently (an edit under `acceptEdits`, anything under `bypassPermissions` without an `ask` rule) never reaches the hook; that was not exercised. `bypassPermissions` still showed a dialog here because an explicit `ask` rule outranked it.
- Subagents: `agent_id` and `agent_type` are present in subagent requests and absent in the main agent's, so a hook request can be attributed to a subagent. Only presence was recorded; matching the value to the transcript's agent id is untested (S7 territory).
- Serialization: two parallel subagent requests produced **two hook invocations at once** (2 log rows before the first answer, 3 of 3), while the terminal showed **one dialog at a time** (the second dialog appeared only after the first was answered, 3 of 3). So hook requests are concurrent per session even though dialogs are serialized.
- Payload extras: MCP requests add the key `mcp_server` and the tool name has the form `mcp__<server>__<tool>`.
- Headless: the hook fires but there is no dialog and nobody to answer, so a "Needs you" entry raised from a `-p` request would be a request no human can answer.
- Safeguards: the scratch work folder only ever held probe files the harness removed, and none of the touch commands ran in any trial (nothing was approved).
- **Side effect (not intended):** the `bypassPermissions` warning screen has to be accepted once, and accepting it wrote `skipDangerousModePermissionPrompt: true` into `~/.claude/settings.json` (its hash changed during the run; the other keys present look like the owner's usual ones, but there is no backup to prove nothing else moved). The owner approved accepting the warning, but the file write was not anticipated. It was not reverted, because it is the owner's file.

## Verdict and consequences

**PASS** (each condition gave a clear fires result in 3 of 3 runs; `agent_id` recorded as present for subagents, absent otherwise).

1. **Mode badge (R45):** show the payload's `permission_mode` verbatim; keep "may skip prompts" wording for `acceptEdits`, `auto` and `bypassPermissions`, because silently allowed calls never reach the hook.
2. **Attribution (A17):** `agent_id` is present for subagents, so the attribution fallback ("unknown") applies only to the main agent (where it is absent by definition); E1 correlation still decides which reducer agent owns the request.
3. **Concurrency:** several requests can be pending at once for one session; keep the per-session cap and oldest-first slot rule (E1 rule 4, R72). The "newer request supersedes older" rule is not needed (requests do not supersede; dialogs queue).
4. **Headless:** hook requests from `-p` runs have no answerable dialog. Task 10's card should not imply the user can answer; the payload gives no signal that tells headless apart, so "answer in the terminal" wording is the safe default, and a later release could add a heuristic.
5. **MCP and non-Bash tools:** render every key of `tool_input` for any `tool_name` (R57 slice 1 already does); `mcp_server` is an extra top-level key to ignore, never to trust.
