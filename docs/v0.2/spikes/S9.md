# Spike S9: Origin and Sec-Fetch-Site on a same-origin WebSocket upgrade

Run 2026-10-19. Header names and counts only. Question (SPEC section 15): do Chromium, Firefox and WebKit send `Origin` and `Sec-Fetch-Site: same-origin` on a WebSocket upgrade from the same-origin page, on `127.0.0.1` and `localhost`? Pass: present in each browser.

Method: Playwright (npm `playwright`, installed with `--ignore-scripts` in a scratch folder, nothing added to the repo) driving each browser. A throwaway Node HTTP server on a random loopback port logs the upgrade request headers and drops the socket. The page, served by the same server, opens `new WebSocket("ws://HOST:PORT/ws")`. A third case opens the socket from a page on a different loopback port (cross-origin) as the control. Builds: Chromium 1248 (headless shell and the full `chromium` channel), WebKit 2370 (27.2), Firefox 1555 (157.0). One run per case.

## Results

| Browser | Case | `Origin` | `Sec-Fetch-Site` |
|---|---|---|---|
| Chromium (headless shell) | same-origin 127.0.0.1 | present, exact | **absent** |
| Chromium (headless shell) | same-origin localhost | present, exact | **absent** |
| Chromium (headless shell) | cross-origin page | present (the page's origin) | absent |
| Chromium (full binary) | all three cases | present, exact | **absent** |
| WebKit | same-origin 127.0.0.1 | present, exact | `same-origin` |
| WebKit | same-origin localhost | present, exact | `same-origin` |
| WebKit | cross-origin page | present (the page's origin) | `same-site` |
| Firefox | not measured | | |

Chromium's upgrade request carried only: `host, connection, pragma, cache-control, user-agent, upgrade, origin, sec-websocket-version, accept-encoding, accept-language, sec-websocket-key, sec-websocket-extensions`. No `Sec-Fetch-*` header at all.

Firefox: the Playwright Firefox build exited at launch ("Could not find profile folder") with a profile in the session scratch folder, in a short `/tmp` path, and with Playwright's default; `firefox --version` itself runs (157.0). Cause not found. Left for the Task 12 harness or a by-hand run.

## Verdict

**FAIL for Chromium as the spec was written; PASS for WebKit; Firefox open.** The spec required `Sec-Fetch-Site: same-origin` on the upgrade for the `verified` flag. Chromium (Chrome, Edge, Brave) never sends it on WebSocket upgrades, so under that rule no Chromium connection could be verified and the read-only card would never receive a `request` push. Tested only on the Playwright-bundled builds, not the owner's installed Chrome.

## Decision applied (owner chose "adopt fix", 2026-10-19)

The `verified` rule for the WebSocket upgrade becomes:

1. Host exact (already enforced), and `Origin` present and exactly `http://127.0.0.1:PORT` or `http://localhost:PORT`.
2. If `Sec-Fetch-Site` is present it must be `same-origin` (WebKit sends it, so a same-site or cross-site page is refused there); if it is absent the connection is still verified (Chromium).

`/api/exchange` is a `fetch` POST, where Chromium does send `Sec-Fetch-Site`, so its stricter rule (Origin present and exact AND `Sec-Fetch-Site: same-origin`) is unchanged; plan Task 6 tests it and the Task 12 harness proves it in real browsers (S9 did not test `fetch`).

Why it is safe enough: `Origin` is set by the browser and a page cannot forge or omit it, and a rebinding or cross-site page carries its own origin, which fails the exact match. A same-uid non-browser client can forge any header, which is the existing same-uid ceiling (SPEC section 2), not a new gap. Cost: `Sec-Fetch-Site` is no longer a second signal on WebSocket upgrades in Chromium, so the real-browser rebinding harness (T-rebind) carries more weight for that route.
