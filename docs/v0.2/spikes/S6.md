# Spike S6: live reload, JSONC, untrusted project hooks, `disableAllHooks`

Run 2026-10-20. Counts only. Question (SPEC section 15, S6): how does Claude Code treat a settings file edited while a session runs, a settings file with a comment or a trailing comma, a project hook in an untrusted folder, and `disableAllHooks` in a project file when our hook comes from another layer? Decides the installer's parser, the install and uninstall wording, and the doctor warnings.

Method: the same scratch setup as S5 (`claude 2.1.302`, Python pty harness, `--setting-sources project,local --permission-mode default --model haiku`, one `ask` rule so every probe shows a dialog, stub hook with `matcher: "*"` that logs and prints nothing, every dialog answered with Esc so nothing ran). The edited file is the project-local `.claude/settings.local.json` in the scratch session folder, because that is the layer the installer writes by default (R14). 25 sessions in total: add 5, remove 5, comment 3, trailing comma 3, `disableAllHooks` 3, untrusted interactive 3, untrusted headless (`-p`) 3 (a four-session pilot of comment, trailing comma, `disableAllHooks` and untrusted is among them).

Safeguards held: the scratch work folder never changed; `~/.claude/settings.json` hash unchanged; the only new entry in `~/.claude.json` is the trust entry for the S5 scratch folder (approved earlier); the untrusted folder was never trusted (the trust prompt was declined every time, so no entry was written for it).

## Results

| Case | Result |
|---|---|
| (a) add a hook to an existing settings file while a session runs; prompt 8 s later | hook fired in 5 of 5 trials (picked up within 8 s, no restart) |
| (b) remove the hook while a session runs; first a baseline prompt, then a prompt 8 s after the edit | baseline fired 5 of 5, then the hook did not fire after the edit 5 of 5 (removal effective within 8 s) |
| (c1) file with a `//` comment and a `/* */` comment | hook did not fire in 3 of 3: Claude Code reported a settings error and ignored the file (strict JSON) |
| (c2) file with a trailing comma | hook did not fire in 3 of 3: same settings error, file ignored |
| (d1) project hook in an untrusted folder, interactive | trust prompt shown before anything else, 0 hook runs while it was open, and the prompt text does not mention hooks; declined 3 of 3 |
| (d2) the same untrusted folder, headless `-p` | **the project hook RAN in 3 of 3, with no trust prompt** (the session exited 0) |
| (e) `disableAllHooks: true` in the project-local file, our hook supplied through `--settings` (the user-level stand-in) | the hook did not fire in 3 of 3: a project file turns off hooks from other layers |

Each fired or did-not-fire result was identical across its trials, so the S6 pass criterion (a consistent observable result) holds for (a), (b), (c), (e) and both halves of (d).

## Verdict and consequences

**PASS (every case consistent).** Design consequences:

1. **Install and uninstall wording (A9, A10):** say that a running session picks up an added or removed hook within a few seconds, without a restart (observed 5 of 5 each), and that this was verified only for the project-local layer. Do not promise it for the user-global file, which this spike did not touch (it would have meant editing the owner's real settings; check it at the owner's first real install, with the owner present).
2. **Parser (R10, R64):** keep the installer strict. A comment or a trailing comma makes Claude Code drop the whole file, so the installer must refuse such a file with a clear message (it must never "fix" it, and never write into one). No tolerant tokenizer is needed. The T-install-fixtures corpus entries for JSONC and trailing commas become "refused, no write".
3. **Project scope and trust (R14):** interactive sessions hold project hooks until the folder is trusted, but headless `-p` runs executed the project hook with no trust step. So a project-scope install is live in every `-p` run in that repo, and a repo's own committed hooks run unprompted in `-p`. The R14 confirm text for project scope and the git-tracked flag must say this. `doctor` should list project hooks in untrusted-or-unknown folders as informational.
4. **`disableAllHooks` (A16, R15):** a project-local `disableAllHooks: true` silences our hook even when it lives in another layer. `doctor` and the install preview must report `disableAllHooks` found in any layer as a warning that the hook will not run, and the page's "hook seen" badge (R17, from real ingests) is the live check.
5. Not covered: managed settings and plugin-supplied hook ordering, and a user-global entry being turned off by a project `disableAllHooks` (only a `--settings` stand-in was used).
